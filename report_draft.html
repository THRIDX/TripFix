INTELLIGENT INTERACTIVE SYSTEMS · A2 · REVIEW DRAFT

TripFix: Keeping Control
Across Chained Travel Disruptions

Counted words: 1,065 · Abstract: 138 · Main report: 927

Abstract

TripFix explores how travellers can retain control when a disrupted trip and their requirements change repeatedly. The developed prototype keeps requirements visible, previews linked consequences, and applies a repair only after confirmation of the current proposal. A browser interface connects to a local Python state engine. Fixed planning rules and sample fares simulate the planner and provider outcomes. Three illustrated episodes follow the same plan: repairing a cancelled flight, bringing forward the required arrival time after confirmation, and recovering from an unsuccessful second repair. The revision adds an explicit boundary between edited and applied requirements, removes empty confirmations, and makes repeated fare events leave state unchanged. Twelve executable checks and browser walkthroughs verify these behaviours. The project provides a compact, inspectable implementation of interaction mechanisms for continuous plan repair. Live booking and payment are outside its current scope.

1. Problem and scope

A1 asked what users need to see and control when successive disruptions and changing requirements affect the same plan. TripFix develops this question through a cancelled London–Lisbon flight. The traveller wants to retain Riverside Hotel, arrive by 22:00 and keep extra cost within £180. A replacement flight also affects a first-day walk. After accepting a repair, the traveller brings the arrival deadline forward to 19:00.

TripTide reports difficulties maintaining itinerary quality under disruptions, particularly for longer plans [1]. A1 used this evidence to motivate continuous repair. This prototype focuses on visible requirements, dependent changes and confirmation across successive decisions. Two fixed flight options make the sequence repeatable. Natural-language input is an optional later extension; live availability, payments and refunds are outside this version.

2. Design rationale

Keep requirements beside the plan. Budget, latest hotel arrival and the protected hotel stay visible across repairs. Lecture 05 links recognition and working memory to cognitive load [3]. Persistent fields let the traveller inspect requirements without recalling earlier exchanges. Hotel protection is fixed for this scenario; budget and time are editable. This deliberately limits the scope while exposing the state that subsequent repairs must preserve.

Separate editing from applying. The audit found that a changed input could appear beside a proposal still based on the previous requirement. The revised interface marks unapplied changes and disables review and confirmation until requirements are applied or restored. Applying them invalidates the old preview. This clarifies the action boundary discussed in Lecture 06 [4]. It adds an explicit step but avoids treating typing as consent to change the plan.

Show the consequences, then request confirmation. The preview compares current and proposed values, showing only changed items. Unchanged hotel and activity information remains visible. This supports the gulf of evaluation [4] and Amershi et al.'s guidance on correction and consequences [2]. For the first repair, the later arrival moves the walk to day two. For the second, the walk stays put; only the flight, arrival and cost change. The explanation follows those actual differences.

Keep confirmation tied to current information. A proposal identifier and state revision prevent outdated or repeated confirmation. New requirements or prices invalidate the proposal; a repeated price event leaves it intact. Lectures 10 and 12 inform these checks on stale context, preconditions and execution boundaries [6,7]. A repair with no differences produces a status message and no confirmation. This avoids adding approval steps that have no consequence.

Support direct correction and recovery. Editable fields provide precise control over the simulated planner. Lecture 07's hybrid-interaction approach informs keeping interpretable state on screen if conversational input is added later [5]. A failed simulated execution preserves the saved plan. Discard removes a preview; undo restores a previous local plan while retaining current requirements and fares. The message asks the traveller to review the restored plan against those current conditions.

3. Architecture and technical choices

HTML, CSS and JavaScript render server snapshots and guard unapplied input. A standard-library Python server routes actions to one in-memory state object. Requirements, proposals, revisions, history and planning rules are logical components within that process. The planner selects the lowest-cost sample flight satisfying budget and arrival limits. Scenario inputs provide fare changes and execution rejection.

The browser requests actions; the engine checks conditions, updates state when appropriate, and returns the outcome. No external provider is called. Extra cost means the selected repair's total additional cost, not accumulated payments across revisions. The application is a single-user local demonstration; restarting it resets state. The architecture diagram distinguishes the implemented control mechanisms, simulated planning and optional language input.

4. Three connected interaction episodes

A — Initial repair. The traveller reviews TF218 at £120, arriving at 20:55. The preview also moves the walk to day two. Confirming saves this local plan while retaining the hotel. Figure 2 shows the proposal and saved result.

B — A changed requirement after confirmation. The traveller edits the deadline to 19:00. The unapplied-input message appears. After applying the requirement and requesting another repair, TF204 is proposed at £170, arriving at 18:55. The saved £120 plan remains visible until confirmation. The hotel and day-two walk stay unchanged (Figure 3).

C — Failure and recovery. The next execution is set to fail. The traveller confirms the second proposal; the rejection leaves the £120 plan intact. Requesting a fresh proposal and confirming again succeeds, updating the same plan to TF204 at £170 (Figure 4). Confirmation and execution outcome remain distinct throughout.

5. Development evidence and evaluation

The initial version established proposals, revisions and local undo. The subsequent audit identified three inconsistencies: unapplied inputs did not block confirmation, identical repairs generated empty previews, and repeated fare events reported a new change. The revision adds the input guard, checks actual differences and compares previous prices. Success messages now list only changed fields. These are recorded with checks and commit references in the README.

All twelve executable tests pass, including three added regressions covering empty repairs, repeated price events and a second repair after confirmation with failure, retry and undo. The browser walkthrough separately checked that editing an unapplied budget disables confirmation, and captured six screens from the continuous sequence. Earlier checks cover stale and duplicate confirmation, invalid input, constraints and cancellation.

Success means preserving active requirements in proposed repairs, exposing changed values before approval, refusing outdated actions and reporting the resulting state accurately. These constructed checks establish behaviour in the selected scenarios; they do not measure user understanding. Further scenario evaluation can vary the order of requirement and price changes without expanding the feature set.
