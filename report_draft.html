TripFix: Keeping Control
Across Chained Travel Disruptions

Counted words: 1,059 · Abstract: 147 · Main report: 912

Abstract

TripFix explores how travellers can remain in control when a disrupted trip changes repeatedly. A cancelled flight may require a new arrival time and a moved activity, while the traveller may also revise their spending limit. This project develops an interactive simulation in which requirements remain visible, proposed changes are reviewed together, and confirmation applies only to the current proposal. A browser interface connects to a local Python state engine. A fixed proposal builder and sample fares simulate the planning component; no live booking service is connected. Three illustrated sequences show an initial repair, a changed budget, and a changed fare followed by an unsuccessful action. Nine executable checks cover constraint preservation, confirmation, outdated previews, cancellation and recovery. These checks establish behaviour within the constructed scenarios; they do not establish travellers' understanding or performance. The prototype provides inspectable interaction evidence for the research questions introduced in A1.

1. Problem and scope

A1 asked what users need to see when successive disruptions and changing requirements affect the same plan. TripFix develops that question through one traveller's cancelled London–Lisbon flight. The traveller wants to retain Riverside Hotel, arrive before 22:00 and spend no more than £180 extra. The replacement flight also affects a first-day activity. The interface must expose this dependency while preserving requirements across later changes.

TripTide evaluates itinerary revision under disruptions and reports weaker performance as itineraries become longer [1]. It motivates testing dependent changes, but does not establish that this interface improves user control. The present scope is a small interactive simulation with fixed travel options. Real availability, payment, refunds and language-model generation remain planned. This scope allows the interaction rules to be inspected without treating plausible sentences as completed bookings.

2. Design rationale

Visible requirements. Budget, latest hotel arrival and the protected hotel appear beside the plan. Lecture 05 connects recognition, working memory and cognitive load: the interface should carry state that users would otherwise have to recall [3]. The budget and time can be edited directly. The protected hotel remains visible during every repair. This makes persistence inspectable, although a later user study would be needed to establish whether travellers notice violations.

Review the consequences together. The preview shows current and proposed flight, hotel-arrival time, activity and extra cost. It explains that the later arrival moves the walk to day two. The hotel is explicitly retained. Lecture 06's gulf of evaluation concerns understanding what happened and whether it matches the goal [4]. Showing linked consequences before confirmation gives the traveller a concrete object to inspect. Amershi et al.'s guidance on correction and consequences also informs this choice [2].

Use precise controls for precise decisions. The first version combines a repair request with visible budget and time fields. Lecture 07 recommends hybrid interaction when conversation carries a request but the screen holds state [5]. A future conversational component can propose changes to these fields. It will still need to display its interpretation. The current simulation exposes the same decision points directly. A blocked repair identifies the incompatible limits and lets the traveller change them; it does not quietly relax the budget or hotel-arrival requirement.

Confirm a current proposal. Each preview carries a unique identifier and the current state revision. Changing a requirement or receiving a new fare invalidates that preview. This applies Lecture 10's concern with stale memory and Lecture 12's precondition and confirmation checks [6,7]. Confirmation must refer to the plan the traveller actually reviewed. A proposal cannot be applied twice. The extra review has an interaction cost, but approval of a materially changed price would otherwise refer to outdated information.

Report outcomes and support recovery. The application constructs its success message after updating local state. A simulated provider rejection leaves the current plan unchanged and reports the failed result. This follows Lecture 12's distinction between a model's claim and the tool's return value [7]. Discard removes an unconfirmed preview. Undo restores a previous local plan while retaining current requirements and fares. The interface calls this a local change; reversing a real booking would require the provider's own cancellation and refund rules.

3. Architecture and developed interaction

The browser renders the current plan, requirements, preview and recent actions from a server snapshot. The Python engine owns revisions, pending proposals and history. The proposal builder selects the lowest-cost available option satisfying the budget and latest-arrival limits, preserves the hotel and moves the dependent walk. This deterministic component simulates the intelligent planner. Scenario fixtures supply prices and a provider failure. Both the simulation and the unconnected external services are identified in the diagram.

The first sequence repairs the cancelled flight: review TF218 at £120 extra, inspect the shifted activity, then confirm the local update. The second changes the budget to £100 while a preview is pending. The old preview disappears and no compliant option is offered. Increasing the limit to £130 permits a fresh £120 proposal; the hotel and arrival limit remain intact. The third changes the fare to £145. The earlier preview becomes unusable. A new proposal can be reviewed, but a simulated provider rejection demonstrates that confirmation does not guarantee execution.

4. Development and checks

Development began with the A1 requirement to follow successive changes. The first implementation separates current plan, user requirements and proposed changes. Revision checks were added so a new budget or price cannot leave an earlier confirmation valid. An explicit result path was then added for unsuccessful execution. The browser uses a single current-state response for each action, keeping the visible plan aligned with the state engine.

Nine executable checks pass. They cover preview without mutation, confirm and undo, a changed budget, repeated budget-and-fare changes, stale confirmation, provider failure, duplicate confirmation, arrival constraints, and cancellation with invalid inputs. The repeated-change check moves through budgets of £130 and £160 around a fare increase, checking that the hotel and latest-arrival limit survive. The failure check asserts that the plan and undo history stay unchanged and that the response reports rejection.

These are behavioural checks on a constructed simulation, not measurements of attention, trust or usability. The next evaluation should replay longer disruption sequences and inspect whether every current requirement is preserved, each material change appears in the preview, and every reported outcome matches the executed result. A future participant study could separately test whether people identify changed costs and dependent activities. Its absence limits claims about reduced effort or improved understanding.
